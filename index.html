00 meencrypt / fishrand v4

We took the opposite security direction.

Password managers assist you. They don't bond with you. MeenCrypt encrypts your diary with a goldfish as witness. The fish conditions the key but adds 0 bits of security, and we say so up front. The math is AES-256-GCM, and an RSA-3072 key wraps it.

01 try it · runs in your browser

Write something. The fish will watch.

This is the package v4 pipeline, rebuilt with WebCrypto. It freezes the tank's current frame, hashes it, and mixes that hash with 32 bytes from your OS's CSPRNG using HKDF. The result seals your entry with AES-256-GCM. An RSA-3072 key wraps the session key, then the session key is thrown away.

diary.txtUSB: not inserted
  1. ●observefreeze a frame from the tank
  2. ●conditionSHA-256(frame) → fish_hash
  3. ●secret32 bytes from the OS CSPRNG
  4. ●deriveHKDF-SHA256(secret ‖ fish_hash)
  5. ●sealAES-256-GCM, 12-byte nonce
  6. ●wrapRSA-OAEP-3072(session key)

★ = the parts that actually protect you. In this demo the "USB" keypair lives in this tab's memory and dies when you refresh. In the real CLI, cli.py keygen writes the private key to your USB stick.

02 how the bytes move

Two lanes. Only one of them is secret.

The upper lane is the ritual: a webcam, OpenCV, an optional ESP32 microphone, and a collector that turns a few seconds of tank into canonical bytes. The lower lane is the defense. The fish's hash does condition the key, but the secret comes from os.urandom.

public observation secret material optional / offline
GOOD fishThe fish are moving enough. SHA-256 of the fish window conditions the key.
MEDIUM fishThe fish are lazy. The fish digest and the audio digest are hashed together.
BAD fishTracking lost the fish. The ESP32 microphone takes over. Either way, the CSPRNG was always doing the work.

06 git log --graph --oneline

Five versions of taking a joke seriously.

*
8c2e213(HEAD → main, v5)polish the tank

Diary entries are now bound to a physical drive by its hardware serial, so a copied key file isn't enough when you decrypt through the app. The ESP32 mic streams over USB serial. The dashboard got live fish-activity and ops-rate charts, quality-tier bars, and a tamper test, and the diary app was reworked. The crypto didn't change, and that's on purpose.

*
c8d7df7(v4)RSA-OAEP hybrid encryption

An RSA-3072 public key now wraps the ephemeral AES-256 session key. The private key lives on a USB stick, and nothing else is needed to decrypt. The fish became audit metadata. When the fish are too still, the ESP32 mic fills in.

*
(v3)the fish-chain

Each frame ate one HMAC-SHA256 step of the key schedule, and a public commitment rejected the wrong fish. This is where we worked out exactly why fish data can never be a secret.

*
(v2)make it real

This added a real vision contract, a collector that watches the NDJSON inbox, and one universal USB code that unlocks everything. The two websites arrived too: a dashboard on :5173 and a diary on :5174.

*
(v1)the joke

SHA-256 of the fish, then HKDF, then AES-GCM. Each package embedded its own random key material, so anyone with the file could decrypt it. It made a perfect demo and a terrible secret.

11 questions we'd ask too

      
FAQ

      

        

          Is this actually secure?
          
Yes. The diary is sealed with AES-256-GCM. RSA-3072-OAEP wraps the session key. Randomness comes from your OS's CSPRNG. That part is standard and tested. The fish is not part of your threat model.

        

        

          What does the fish actually contribute?
          
OpenCV watches it, and an optional ESP32 mic listens in. That observation is canonicalized, hashed with SHA-256, and fed into HKDF as a fingerprint of the moment. It is not a source of randomness. Anyone with the same webcam feed could reconstruct it, so it can never be secret.

        

        

          Do I need the fish to decrypt?
          
No. Since v4, only the RSA private key is needed. The fish hash stays in the package as audit metadata about the tank at the moment you wrote. It never controls whether you can decrypt.

        

        

          What if someone copies my private key file?
          
Entries you write in the diary app are bound to the physical drive their key was saved to, identified by the drive's hardware serial. Without that exact drive plugged in, the server refuses with "insert the drive this entry needs". To be honest about it: the server enforces this check on top of the crypto. It is not part of the encryption, and the CLI with the key file alone can still decrypt.

        

        

          What happens if I lose the USB drive?
          
The diary stays encrypted forever. There's no recovery flow and no backdoor. That is the design, not a bug.

        

        

          Do I need the microphone?
          
No. The vision tracker alone runs the full pipeline. The mic only steps in when the fish are too still to track well.

        

        

          Why does this exist?
          
TinkerHub's "Useless Projects" hackathon asked for real engineering behind a deliberately unnecessary idea. This is that.
